# PortfolioHub

PortfolioHub — небольшое Laravel-приложение для публикации карточек проектов с изображениями, технологиями и внешними ссылками. Проект намеренно оставлен компактным: доменная логика следует стандартным Laravel-подходам, а публичный интерфейс построен на Inertia и Vue.

## Стек

- PHP 8.3
- Laravel 13
- Inertia.js
- Vue 3
- Tailwind CSS 4
- SQLite по умолчанию для локальной разработки и тестов
- PHPUnit
- Laravel Pint
- GitHub Actions

## Возможности

- Публичная главная страница со списком опубликованных проектов.
- Каталог всех проектов с поиском и фильтрацией по технологиям.
- Детальная страница проекта в формате небольшого case study.
- Галерея проекта с выбором изображения.
- Технологии проекта через связь many-to-many.
- Контактная форма с валидацией и сохранением сообщений.
- Защищённая админка для управления проектами и контактными сообщениями.
- Загрузка изображений проекта в админке с сохранением в public storage.
- Управление галереей проекта: drag and drop, порядок изображений и выбор главного изображения.
- Отдельное управление технологиями в админке.
- Защита важных демо-проектов от редактирования и удаления в публичной админке.
- Идемпотентные сидеры для демо-данных и изображений.
- CI-проверки Composer metadata, PHP code style, frontend build и тестов.
- Deploy jobs для staging и production на push-событиях.

## Архитектура

Главная страница `GET /` работает как витрина: `HomeController` загружает опубликованные проекты, eager-load'ит изображения и технологии, сортирует проекты по `published_at` в порядке убывания, ограничивает выборку шестью записями и передаёт данные в Inertia-страницу `Home/Index` через `ProjectCardResource`.

Каталог `GET /projects` показывает опубликованные проекты с поиском и фильтрацией по технологиям. Детальная страница `GET /projects/{project:slug}` отдаёт расширенный контракт через `ProjectDetailResource`. Контактная форма отправляется через `POST /contact` и валидируется отдельным Form Request.

Админка находится под `/admin` и защищена стандартной session-auth аутентификацией Laravel. Сохранение проекта вынесено в action, потому что операция должна быть атомарной: поля проекта, связи с технологиями и изображения сохраняются в одной транзакции. Slug проекта генерируется автоматически из названия. Загруженные через админку изображения сохраняются в `storage/app/public/projects/{slug}`, а в БД хранится storage-relative путь. Порядок галереи управляется из интерфейса; первое изображение используется как главное. Важные демо-проекты можно пометить как защищённые, чтобы публичный demo-доступ не мог их изменить или удалить. Технологии управляются отдельным CRUD-разделом; технологии, связанные с защищёнными проектами, нельзя изменить или удалить из demo-админки.

Отдельные service/repository-слои не добавлены, потому что текущий функционал небольшой. Для этого масштаба достаточно Eloquent-моделей, ресурсов, миграций, фабрик, сидеров и feature-тестов.

## База данных

Основные сущности:

- `projects`: название, slug, описание, опциональные ссылки на сайт и репозиторий, дата публикации, флаг защиты от demo-редактирования.
- `project_images`: storage-relative путь к изображению, alt-текст, порядок сортировки, связь с проектом.
- `technologies`: уникальные название и slug технологии.
- `project_technology`: pivot-таблица между проектами и технологиями.
- `contact_messages`: сообщения из контактной формы, email, статус прочтения, timestamps.

Индексы и ограничения:

- `projects.slug` уникален.
- `projects.published_at` индексирован для запроса главной страницы.
- `project_images` удаляются каскадно вместе с проектом.
- `project_images` имеет unique-ограничение `(project_id, sort_order)`.
- `project_technology` использует составной primary key и каскадное удаление.
- `contact_messages.created_at` индексирован для просмотра новых сообщений.

## Работа с данными

Запросы главной, каталога и детальной страницы заранее загружают связи `images` и `technologies` до преобразования данных ресурсами. Это упрощает frontend-контракт и предотвращает N+1-запросы при рендеринге карточек и страницы проекта.

## Локальный запуск

```bash
composer install
npm install
cp .env.example .env
php artisan key:generate
php artisan migrate --seed
php artisan storage:link
npm run dev
php artisan serve
```

Локальный пользователь для демонстрации админки после `php artisan migrate --seed`:

```text
admin@example.com
password
```

Админка:

```text
/login
/admin
```

Production-сборка фронтенда:

```bash
npm run build
```

## Тесты и проверки

```bash
composer validate --strict
vendor/bin/pint --test
php artisan test
npm run build
```

Автоформатирование через Pint:

```bash
vendor/bin/pint
```

Тесты используют SQLite in-memory базу и отключают Vite через стандартный Laravel-хелпер `withoutVite()`, поэтому `php artisan test` работает на fresh checkout без предварительного `npm run build` и без закоммиченных build-артефактов.

## CI/CD

GitHub Actions запускает проверки на pull request и push в ветки `main` и `develop`. Job `tests` валидирует Composer-конфигурацию, проверяет PHP-стиль через Pint, устанавливает Node-зависимости, собирает frontend, проверяет build-артефакты и запускает PHP-тесты.

Push-события также могут запускать deploy:

- `develop` деплоится на staging.
- `main` деплоится на production.

Deploy jobs используют frontend build artifact, созданный в test job.
