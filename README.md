# PortfolioHub

PortfolioHub — мой небольшой fullstack-проект на Laravel, Inertia и Vue.

Я делал его как публичный пример кода для PHP/Laravel-вакансий: не как большой учебный комбайн, а как компактное приложение, где можно посмотреть backend, базу данных, frontend, тесты и CI в одной понятной задаче.

Идея простая: это портфолио проектов с публичной витриной, каталогом, страницами проектов, контактной формой и демо-админкой.

## Что можно посмотреть

- публичную главную страницу с проектами;
- каталог проектов с поиском и фильтром по технологиям;
- страницу проекта в формате case study;
- галерею проекта с несколькими изображениями;
- контактную форму с валидацией и сохранением сообщений;
- админку для управления проектами, технологиями и сообщениями;
- загрузку изображений с обработкой в WebP и генерацией размеров для разных мест интерфейса;
- защиту демо-данных через роли `demo` и `owner`;
- feature-тесты, миграции, сидеры и GitHub Actions.

## Демо-админка

После сидов доступен демо-пользователь:

```text
admin@example.com
password
```

Это именно демо-доступ. Он позволяет зайти в админку и посмотреть, как работает CRUD, но не даёт редактировать или удалять защищённые проекты.

Для реального владельца есть роль `owner`. Такого пользователя я не добавляю в сидеры намеренно: в публичном репозитории не должен лежать настоящий админ-доступ. В локальном или production-окружении owner создаётся отдельно.

## Как устроен проект

Публичная часть отдаётся через Inertia. Контроллеры загружают данные через Eloquent, заранее подгружают нужные связи и передают во frontend готовые Resource-контракты.

Основные страницы:

- `/` — главная страница с несколькими проектами;
- `/projects` — каталог всех опубликованных проектов;
- `/projects/{slug}` — детальная страница проекта;
- `/login` — вход в админку;
- `/admin` — панель управления.

Проекты связаны с технологиями через many-to-many. Изображения проекта лежат отдельной таблицей и сортируются по порядку. Первое изображение используется как главное.

Сохранение проекта вынесено в отдельный action, потому что это атомарная операция: нужно обновить сам проект, технологии, старые изображения и новые загруженные файлы. Для такой логики транзакция полезнее, чем разносить всё по контроллеру.

## База данных

Основные таблицы:

- `users` — пользователи админки с ролью `demo` или `owner`;
- `projects` — проекты, slug, описание, ссылки, даты, публикация и защита демо-данных;
- `project_images` — изображения проекта и пути к подготовленным размерам;
- `technologies` — технологии;
- `project_technology` — связь проектов и технологий;
- `contact_messages` — сообщения из контактной формы.

В миграциях есть ограничения и индексы там, где они нужны: уникальные slug, foreign keys, cascade delete, индекс публикации проектов, составной ключ в pivot-таблице.

## Изображения

В админке можно загрузить до 5 изображений на проект. Файлы сохраняются в public storage, конвертируются в WebP и получают несколько размеров:

- large — для детальной страницы;
- card — для карточек проекта;
- thumb — для миниатюр.

Так frontend не тянет оригиналы туда, где нужны маленькие изображения.

## Почему без лишней архитектуры

Я не добавлял Repository/Service/DTO просто ради вида. В проекте есть слой action для сохранения проекта, потому что там появилась реальная транзакционная логика. Остальное оставлено ближе к стандартному Laravel: Form Requests, Resources, Eloquent-модели, миграции, фабрики и feature-тесты.

Для такого размера проекта это читается проще и честнее.

## Локальный запуск

```bash
composer install
npm install
cp .env.example .env
php artisan key:generate
php artisan migrate --seed
php artisan storage:link
npm run dev
php artisan serve
```

Production-сборка frontend:

```bash
npm run build
```

## Проверки

```bash
composer validate --strict
vendor/bin/pint --test
php artisan test
npm run build
```

Тесты используют SQLite in-memory базу. Для feature-тестов Vite отключён через стандартный Laravel-хелпер `withoutVite()`, поэтому backend-тесты можно запускать без предварительной frontend-сборки.

## CI/CD

GitHub Actions запускает проверки на pull request и push в `main` и `develop`:

- валидация `composer.json`;
- проверка code style через Pint;
- сборка frontend;
- запуск тестов.

Для `develop` и `main` также предусмотрены отдельные deploy jobs под staging и production.

## Что здесь важно для code review

В этом проекте я хотел показать не количество фич, а аккуратность:

- понятные миграции и связи в БД;
- отсутствие N+1 в публичных списках проектов;
- валидацию пользовательского ввода через Form Requests;
- Resources как явный контракт между Laravel и Vue;
- транзакционное сохранение проекта;
- обработку изображений на backend;
- роли для безопасной демо-админки;
- feature-тесты на основные пользовательские сценарии;
- рабочий CI.
